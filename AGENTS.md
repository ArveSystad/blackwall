# AGENTS.md

Guidance for coding agents working in this repo.

## What this is

blackwall is a local, single-user, browser-based control room that runs Claude Code, GitHub Copilot CLI and OpenCode as headless subprocesses against the user's git repos. Agents run on any of the CLIs and plan, grill, implement and review each other's work on tasks from Jira Cloud, GitHub/GHE PRs and issues, or Blackwall tasks you write yourself (free text); the user approves plans, answers questions, triages findings and confirms every outbound action.

This file plus the code are the design reference. User-facing docs are in [`README.md`](README.md).

## Layout

- `apps/server`: Hono HTTP + WebSocket on 127.0.0.1 with launch-token auth (`auth.ts`). Serves the built SPA; routes are wired in `app.ts`. `start.ts` holds the startup shared by both entries: `index.ts` (`pnpm start`) and `desktop-entry.ts` (the desktop shell's child).
- `apps/desktop`: Electron entry `launch.js` (plain JS: rebuilds when stale, then loads `dist/main.js`; `--create-shortcut` writes the Windows Start Menu shortcut). Electron main process: forks the server (`apps/server/src/desktop-entry.ts`) on system Node, tray, badge, quit prompt; draws its own title bar that follows the theme (`title-bar.ts`, the page's `theme-color` meta tag). Electron-free logic sits in its own modules so Vitest can test it; `main.ts` only wires Electron to them. In `apps/web`, layers that can cover the top of the window (portals, fixed overlays, popovers) need `bw-no-drag`, and fixed or full-height layouts must leave `var(--bw-titlebar-h)` free at the top.
- `apps/web`: React + Vite, TanStack Router + Query, Tailwind v4 + shadcn/ui.
- `packages/core`:
  - `pipeline/`: engine, transitions, scheduler, backlog runner, delivery.
  - `agents/`: CLI adapters (`adapters/`, with recorded JSONL fixtures), prompts, permissions and seeds. The adapters are the source of truth for CLI flags.
  - `git/`, `repos/`, `connections/`, `secrets/`, `settings/`.
  - `data/`: export and import of the database (`createDataService`).
  - `db/`: SQLite via better-sqlite3 + Drizzle; migrations in `packages/core/drizzle/`.
  - `playbooks/`: vendored third-party review playbooks, excluded from prettier and eslint (see each folder's `SOURCE.md`).
- `packages/integrations`: Jira Cloud and GitHub/GHE (Octokit) clients, with fixtures.
- `packages/shared`: zod domain and protocol schemas shared by server and web.
- `scripts/start.js`: the `pnpm start` launcher. `scripts/desktop.js`: the `pnpm desktop` launcher. `start.ps1`: the dev launcher on Windows.
- `docs/design/`: UI mockups; `bw.css` is the token source.

## Commands

- `pnpm install`
- `pnpm dev`: server under `tsx watch` plus the Vite dev server.
- `pnpm desktop`: builds if needed, then runs the Electron shell.
- `pnpm build`
- `pnpm typecheck`
- `pnpm test`: Vitest against sources, no build needed.
- `pnpm lint`
- `pnpm format:check` (`pnpm format` to fix).
- Real-CLI and keyring tests are opt-in: `BLACKWALL_TEST_CLIS=1`, `BLACKWALL_TEST_KEYRING=1`.
- Before finishing a change, run `pnpm typecheck && pnpm lint && pnpm test`.

## Conventions

- TypeScript strict, ESM, Node 22+.
- Prettier: width 100, double quotes, trailing commas. LF line endings, 2-space indent (`.editorconfig`).
- Tests sit next to sources as `*.test.ts`.
- Shared types and schemas go in `packages/shared`.
- A DB schema change needs a new Drizzle migration (`packages/core/drizzle.config.ts`).
- Match the surrounding comment density and naming.
- UI work follows [`.claude/skills/blackwall-design/SKILL.md`](.claude/skills/blackwall-design/SKILL.md).
- Conventional commits, for example "feat(feature-name): description of feature" or "chore(skills): remove obsolete skill"

## Design rules

- **Domain:** a Task has one origin (`jira-issue` | `github-pr` | `github-issue` | `free-text`, shown as "Blackwall") and one or more Runs; Runs are made of Steps; Findings carry a severity and tags.
- **Agents:** CLI-agnostic. A task runs its agents on its repo's default CLI (copied onto the task when it is created), with optional per-agent overrides per task. Each step records the CLI it ran on. Models and permission overrides are set per CLI on the agent.
- **Pipeline:** Inform → Plan review/grill → plan approval → Implement → Checks → Code review → Summarize → finish. Review PR mode: Inform → review panel → triage → inline PR comments, no plan or implement; at triage the user can step through the diff hunk by hunk and comment on it, or send an instruction from the chat, which re-runs the review panel over the whole PR with that instruction and returns to triage. The task's Context reaches the code reviewers. Summarize writes the full in-app summary and a short outward summary of the behavioural/visual change, and may propose up to 5 follow-up tasks, stored on the task; a task that only analyses code may change nothing and deliver its follow-ups as its whole output.
- **Checks:** per-repo commands run after each implement round; a failure goes back to the implementer and becomes a Critical `correctness` finding if it persists.
- **Grill:** plan reviewers ask questions; the planner answers what the repo can settle, the rest go to the user. Nothing is implemented before the user approves the plan.
- **Worktrees:** one per task at `../<repo>.worktrees/<task>`.
- **Branches:** PR tasks use the PR head branch. Jira tasks use `feature/<key>-<slug>`, or `fix/…` when the issue is a Bug. GitHub issue tasks use `feature/<number>-<slug>`, or `fix/…` when the issue has a `bug` label. Blackwall (`free-text`) tasks use `agent/<task-id>`, then rebase and `merge --ff-only` into the repo's local default branch at finish, or, when the user chooses the PR route, are renamed to `feat/<slug>`, or `fix/…` when the squash message's type is `fix` (slug ≤ 30 characters, `-2`, `-3`, … on collision with a local or remote-tracking branch), before the first push. The default branch is set per repo (default `main`); new task branches fork from it and PRs target it. Before new work starts (Inform, Plan review, the first Implement round), a non-PR task branch with no commits of its own and a clean worktree is fast-forwarded to `origin/<default>` (fetched just before, best effort) when the local default branch is an ancestor of it, else to the local default branch. The pipeline never pushes, pulls or moves the default branch itself.
- **Commits:** the harness commits once per implement/fix round, not the agents. Every commit message is a Conventional Commits message, in every repo: the harness puts `chore:` in front when the summarizer's reply has no valid type, and the Jira key, when there is one, goes after the type prefix (`feat(login): ABC-1 …`).
- **Delivery:** only at finish, after explicit confirmation of each listed action. No Jira transitions. Blackwall (`free-text`) tasks offer `merge-main` (ticked by default) or, with a GitHub/GHE remote, `push-branch` + `open-pr` against the default branch, never both; once the branch is pushed they are offered only the push and PR, and are never merged locally. GitHub issue tasks push, open a PR whose body ends `Closes owner/repo#n`, and comment on the issue (`issue-comment`). PR bodies and finish comments carry the short summary and stay brief; implementation details live only in the in-app summary. GitHub issue tasks may also comment on the issue when created and at plan approval; the plan-approval draft names the branch but not the plan. Each comment is opted into and confirmed by the user, never posted by an agent, and is logged on an existing step rather than a new one. Delete is refused while a plan-approval comment is posting. While delivery runs the task stays `needs-you` at its gate with `delivering` set; its pill reads "Finishing". A Review PR task approves the PR only when the user ticks Approve at triage. It defaults to ticked only when no findings are offered. A task delivered before (after Fix CI) adds the new targets to `deliveryTargets`, is not offered `open-pr` again, and squashes only the commits after `origin/<branch>`, so nothing pushed is rewritten; the code actions are still offered whenever the branch has commits since its fork point, so a Fix CI round without a new commit can push again. Pushes never force. When the push of a PR task's branch, or of a branch an earlier delivery pushed, is rejected because the remote branch moved on, delivery fetches it, rebases onto `origin/<branch>` (conflicts go to the implementer, as with `merge-main`) and pushes again. A first push never integrates: a remote branch it did not create fails with what to do.
- **Git failures:** every harness git call classifies git's message (`classifyGitError`; git runs with `LC_ALL=C`). Lock errors on single-step commands (add, commit, reset, checkout, branch, update-ref, merge, fetch, push) and network errors on fetch and push are retried briefly. A `.lock` file inside the repo's git directory that is older than 2 minutes is removed while blackwall has no git command running. Rebases and worktree commands are never retried; a half-created worktree (leftover branch, empty folder, registration without a folder) is picked up on retry. Every git failure shown to the user (step, task, delivery, repository push) says what is wrong and what to do (`describeGitError`), with credentials stripped.
- **CI:** after a delivery pushes the branch to a GitHub/GHE remote (`push-branch`), the CI watcher (`createCiWatcher`) polls the check runs and commit statuses of the pushed `HEAD` and stores the result on the task (`tasks.ci`: `pending | passed | failed | timed-out | none | unavailable`, with each check and its link). It polls after 30 s, then 1.5× longer each time up to 5 min, until every check completes; it gives up after 60 min (`timed-out`), and with no checks after 3 min reports `none`. Watches live in memory; startup and a data import resume pending ones. Each repo can turn watching off (`repos.watch_ci`, Settings → Repositories). Rate limits are transient: the watcher retries every 10 s within the cap, keeps the stored state and shows no hint. Network errors and 5xx back off as usual. A token without SAML SSO authorisation, without Checks/Commit statuses read, or a missing token gives a hint instead of an error (`unavailable` when check runs can't be read and there are no statuses); a background watch never opens the token modal. A done task whose CI failed shows under Needs you (`ciNeedsYou`) until it is archived. **Fix CI** (`fixCi`, `POST /api/tasks/:id/ci/fix`) adds one Critical force-fixed finding per failing check (at most 10) with the end of its log, in a new run, and starts a fix round; the normal loop (Checks, Code review, Aggregate, Summarize) follows and stops at the finish gate, where the user confirms the push again.
- **Fetch comments and fix** (`fixPrComments`, `POST /api/tasks/:id/pr-comments/fix`): offered on a done work task whose delivery opened a PR (`deliveryTargets` has `open-pr`); the PR link comes from the last `open-pr` `delivery.done` event. It reads the PR's review threads (outdated ones too) and conversation, skipping comments signed by blackwall, and adds one High force-fixed finding per thread with new comments plus one for new conversation comments and review summaries. Only a current RIGHT-side thread gets line numbers; outdated and base-side threads name the file and say where they were. Each new comment's permalink is recorded in the finding's explanation as `Comment: <url>`, and a comment whose permalink any finding of the task already carries is not fixed again (a new reply gets a finding with the earlier thread as context). At most 20 findings per call; the rest come on the next. It cancels the CI watch (the next push restarts it), starts a fix round and stops at the finish gate, like Fix CI. Nothing new is a 409 ("No new comments on the pull request to fix").
- **Follow-up tasks:** `create-tasks` is a delivery action like the others, offered last (after `merge-main`) when Summarize proposed follow-ups, with a checkbox per item and its target repo. Nothing is created until the user confirms; the picked items are added in one transaction as independent free-text `waiting` backlog items (`dependsOn: []`, `sourceTaskId` set), and `backlog.changed` lets each repo's runner pick them up. Follow-ups must stand alone; multi-step work chains because a follow-up's description lists the later steps and its own Summarize proposes them as its follow-ups. A branch with no commits of its own offers no push, PR or merge.
- **Stacked PRs:** adding a PR that belongs to a stack (from the new task form or Review requests) also adds waiting Review PR backlog items for the stack's other open PRs, skipping PRs an unarchived task or waiting backlog item already covers. They run only through the backlog runner. The stack is found by walking base/head branches between open same-repo PRs, stopping at the default branch and at forks in the tree. `origin.stack` (the stack's PR numbers, bottom first) is set by the server only; client-sent values are dropped. The Backlog shows it as "stack #<bottom> · i/n". Code reviewers of a stacked PR get the other PRs' diffs as context only, and report findings only on their own PR.
- **Findings:** Critical and High gate the loop. At most 3 fix rounds, then escalate to the user. The user can force-fix or force-ignore any finding at any severity; force-fixing one at the finish gate, or while the summary is being written, runs one more fix round right away. Hunk comments from the Diff tab's step-through become force-fixed findings with neither a step nor a reviewer (`isUserComment`); sending them at the finish or escalation gate runs a fix round right away (at escalation that counts as "revise"), and at triage they are fixed in the round that approving triage starts. In Review PR tasks, hunk comments at triage become open findings with neither a step nor a reviewer, posted to the PR as plain inline comments without a severity or title, and queue nothing. At Review PR triage the user can also delete any unfixed finding, with the duplicates merged into it (`deleteFinding`, `finding.deleted`); work tasks only force-ignore. In Review PR tasks the Diff step-through also works while the review runs: each hunk shows its findings as each reviewer's are stored, and the PR's GitHub review threads, polled every 20 s only while stepping through (`GET /api/tasks/:id/pr-comments`, which reports failures as `error` instead of opening the token modal). Drafts can be written at any time, but comments are still sent only at triage. Code reviewers are given the PR's existing comments (a snapshot per review visit) and told not to repeat them.
- **Scratch folder and artifacts:** `.blackwall/` in a worktree is self-ignored by a harness-written `.gitignore` (`SCRATCH_DIR` in `@blackwall/shared`) and never committed. Implementers may save any file to `.blackwall/artifacts/`, served read-only per task (`pipeline/artifacts.ts`): no symlinks, no dotfiles; images and text are capped at `MAX_ARTIFACT_BYTES`, and other files stream as downloads of any size. The extension picks the kind: raster images are served as themselves, known text and code (HTML and SVG included) as `text/plain`, and anything else as an `application/octet-stream` attachment. Every response carries `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, so untrusted output never runs as script. Every code review visit copies the OWASP Secure Agent Playbook afresh into `.blackwall/playbooks/` (`pipeline/playbook.ts`), and the Security reviewer seed prompt points at it.
- **Permissions:** under Locked and Trusted (see Trust), reviewers are read-only (read tools + safe git). Implementers can edit and use the shell, but `git push`, `gh` and anything touching remotes is denied. Implementers are confined to the worktree. Read-only agents (planner, reviewers, summarizer) and the repo chat may also read reference repos, passed per step as `readDirs`: no writes and no git there. The repo chat reads the repo's list (Settings → Repositories); a task's chat reads the task's own `referenceRepoIds`, like its agents. A task reads its own `referenceRepoIds`, copied from the repo when the task is created unless the new task form or backlog item overrode it (`BacklogItem.referenceRepoIds` null = follow the repo until promotion); later repo edits don't change it.
  - Claude, Copilot and OpenCode implementers get the harness-defined `blackwall-worker` sub-agent, which follows the same rules. Claude's built-in sub-agents are denied. Copilot cannot restrict its `task` tool to one agent, so its built-in sub-agents stay reachable, bound by the same deny rules. Copilot reviewers lose the `task` tool. OpenCode's `task` is limited to `blackwall-worker`, its built-in `general` and `explore` sub-agents are denied, and OpenCode reviewers have `task` denied.
- **Trust:** each repo has an agent trust level (`repos.agent_trust`, Settings → Repositories). **Locked** (default) is the harness sandbox. **Trusted** also loads the repo's own skills, sub-agents and instruction files; its project MCP servers (`trust_project_mcp`) and hooks (`trust_project_hooks`) are opt-in and reach implement steps only. **Unrestricted** runs each CLI in its own allow-everything mode, with no rules at all.
  - Read-only steps under Trusted keep exactly Locked's tool permissions, in three layers: no project permissions (Claude stays `--restricted` and gets copies of the repo's skills and agents through a harness `--plugin-dir`, its `CLAUDE.md` in the system prompt; OpenCode keeps project config disabled and gets the repo's skill folders, agents and instructions injected), the Claude guard hook (`packages/core/hooks/guard-readonly.mjs`, a `PreToolUse` hook in `--settings` reading its allowed Bash prefixes from `BLACKWALL_GUARD_ALLOW`; it denies the edit tools, other commands and shell operators, and beats a skill's `allowed-tools`), and the engine's backstop: a snapshot of HEAD, the index tree and the full working tree (`snapshotWorktree`) before the step and after it; any change is undone (`restoreWorktree`) and fails the step ("A read-only agent changed the worktree under Trusted"). The snapshot is taken from the state the step starts in, so the summarizer's staged commit rounds work. Unrestricted has no backstop.
  - A task that runs code the user didn't write is forced Locked (`effectiveTrust` in `@blackwall/shared`): Review PR tasks, and work PR tasks whose branch is not known to hold only the user's commits. `tasks.pr_branch` is `unchecked` (new and backfilled PR tasks, or a failed check), `owned` or `foreign`; the engine checks it (`prBranchOwned`: same repo as the base, the user's PR, every commit authored by the user) at the start of each drive and before a delivery's conflict resolver, on repos above Locked only.
  - Each agent step records the level it ran under (`steps.trust`, `steps.trust_forced`); the task header, inbox cards, repo rows and the Output panel show it, and the finish gate warns when a step ran Unrestricted.
  - Copilot has no way to load the repo's config without the user's own `~/.copilot` (which also holds its login), so Copilot Trusted steps load the user's global agents, skills and MCP servers too; `TRUSTED_LOADS_GLOBAL_CONFIG` lists such CLIs and drives the warnings. Copilot also loads a repo's skills, MCP servers and hooks by itself in a folder the user trusts (`trustedFolders`); Locked removes its `skill` tool.
  - The chat always runs Locked.
- **Chat:** one conversation per repo, plus one per task (`chat_messages.task_id`, `/api/repos/:repoId/tasks/:taskId/chat`), stored in `chat_messages` and loaded on first use (`createChatService`, `/api/repos/:repoId/chat`, `chat.upserted`). On a task's page the panel shows that task's conversation (chosen from the route, never falling back to the repo chat), which always focuses the task; the repo chat never has a focused task. Deleting a task ends its chat turn before the worktree is removed (`beforeDelete` → `forgetTask`). Each message runs the repo's default CLI once, headless and read-only in the repo's checkout, or, when the conversation's task has a worktree on disk, in that worktree (so it can read the files and run the safe git commands there), with the planner's model on that CLI, continuing the chat's CLI session when one is stored for the same CLI and was run in the same directory (a session loaded after a restart has an unknown directory and is tried), and otherwise starting a new session carrying the last 20 user/assistant messages in the prompt; the prompt also carries a fresh block of the repo's tasks (with the error of failed and interrupted ones, and the open user questions of tasks at the `questions` gate) and backlog. A task's conversation uses that task's repo, and its prompt adds a `Focused task` section with its status, gate, error, plan (each capped at about 4000 characters) and open questions, and, when the turn runs in the task's worktree, its path, branch and fork point. The agent replies with markdown plus proposed actions (`create-task`, `message-task` at a gate, `answer-question` at the `questions` gate, `stop-task`, `resume-task` with an optional `message`). A resume message is guidance: it is appended to the prompt of only the agent steps of the resumed visit that failed or were interrupted (not to succeeded steps, new or `fresh` steps, or later stages), and it is refused for a task stopped at a gate, which goes back to its gate. The task view has no input bar: the chat composer's direct button (Mod+Shift+Enter) sends the draft straight to the focused task, to its gate (`messageRoute`) or as resume guidance, without asking the agent and without storing it in the chat. Actions are proposals: the user applies each through the existing endpoints, then the server records it as applied so it cannot be applied twice. "Turn into task" on an assistant reply adds a `create-task` card to it (`POST /api/repos/:repoId/chat/messages/:messageId/actions`), titled with the first line and described by the whole reply. `/clear` aborts that conversation's answer, resets its session and deletes its stored history; the web asks for confirmation first while an answer runs. Chat turns hold no scheduler slot and don't report usage limits to the quota tracker.
- **Export/import:** an export is a zip of `manifest.json` (format, migration level) and a `VACUUM INTO` copy of the database with `token_set` cleared; tokens are never read or exported. Leaving transcripts out drops only the transcript step events (`TRANSCRIPT_EVENT_TYPES`); the rest are pipeline state. An import is refused while any task is running, queued or delivering; it checks the archive, migrates an older one, refuses a newer one, backs up to `<dataDir>/backups/` and replaces every row in the live connection in one transaction, then re-reads the keychain per connection and publishes `data.imported`. Imported running or queued tasks become interrupted (`IMPORT_INTERRUPTED_ERROR`). A task whose worktree folder is missing fails on resume and shows empty diffs.
- **Search:** `GET /api/search` (LIKE over tasks, unpromoted backlog items and repo names, current repo first) backs the Ctrl+K palette.
- **Concurrency:** up to 3 tasks per repo by default (configurable); one active task per branch. Tasks waiting on the user don't hold a slot.
- **Resume:** on shutdown the child CLIs are killed; in-flight steps become interrupted and resume with `--resume <sessionId>` in the same worktree; if the CLI no longer has the session (Claude: `No conversation found`; Copilot: `No session, task, or name matched`; OpenCode: `Session not found`), the step starts afresh with its original prompt.

## Hard rules

- Bind only to 127.0.0.1.
- Tokens live in the OS keychain or `BLACKWALL_TOKEN_*` env vars. They are never sent to the browser or stored in SQLite.
- Agents never push, except that Unrestricted agents are not stopped from it (the finish gate warns). A repo's default branch is pushed only when the user clicks Push on its Backlog and confirms it; the pipeline never pushes it.
  - The Backlog header shows "Push N commits to <branch>" when the local default branch is ahead of `origin/<branch>`. It only ever pushes that branch, never fetches itself (task starts refresh `origin/<branch>`, see Branches) and never forces (`RepoService.push`, outside `GitService`).
  - `main`, `master` and the repo's default branch are always protected: the harness never pushes, finishes or deletes them.

## Task workflow

- Work items move `tasks/backlog/` → `tasks/in-progress/` → `tasks/done/`, named `NNNN-short-summary.md` with frontmatter. The folders are created on demand.
- When a task is done, append an entry to [`tasks/done.md`](tasks/done.md).
- Slash commands for this live in [`.claude/commands/`](.claude/commands/).
